# Guild notices and chat

Open **Guild → Notice board** from the Eternia services menu. The native Citadel page lists notices with pinned notices first, displays their full text, and provides a multiline editor. Use **Refresh** to retrieve new posts; the board does not poll continuously. The current roster also displays online/offline connection presence and offers named confirmations for member removal and leadership transfer.

Members need `board.read` to read the board and `board.post` to publish notices or edit their own text. A moderator with `board.moderate` can pin, unpin or remove a notice, but cannot rewrite another author's words. There are at most 100 active notices and five pinned notices per guild. Titles allow 80 characters and notice bodies 2,000; bodies support line breaks and tabs. Removed posts remain in durable storage for audit instead of being deleted from the database.

Publishing, editing and moderation show a confirmation containing the notice title. The server stores the selected post UUID, revision, draft text and intended guild independently of client action payloads. Confirmation rechecks membership and permissions inside the domain transaction. A changed revision rejects stale edits and moderation. A new notice drafted for one guild cannot be published to a different guild after a membership change. A publication receipt makes a retry of the same submission idempotent. Board reads and writes run on the services executor, away from world ticks.

Use `/e guildchat <message>` for a private live message to online members of your current guild. Both the sender and each recipient must still have `guild.chat` when the message is delivered. It never falls back to public chat, and disconnected members receive no delayed copy. Messages contain 1–500 characters, reject control characters and extra lines, and have a two-second sender cooldown. Chat is ephemeral; use a notice for information members should read later. The command uses native server chat packets and makes no network requests to external messaging services.

The native surfaces are [GuildBoardPage.java](../../src/main/java/com/hexvane/eterniamod/socialui/GuildBoardPage.java), [GuildBoardPage.ui](../../src/main/resources/Common/UI/Custom/EterniaMod/GuildBoardPage.ui), and [EterniaGuildChatCommand.java](../../src/main/java/com/hexvane/eterniamod/command/EterniaGuildChatCommand.java). Persistent permissions, revision checks, size limits and receipts live in [GuildCommunicationService.java](../../src/main/java/com/hexvane/eterniamod/domain/GuildCommunicationService.java). New board surfaces should call that service rather than editing storage rows or granting access from client-supplied guild IDs.

Automated domain tests cover membership/author/moderator authority, stale revisions, the changed-guild draft case and receipt replay. Command tests cover length and single-line control-character rejection. Final readable layout, keyboard entry and live multi-player delivery still need a client acceptance session; loading server assets alone does not verify those interactions.
